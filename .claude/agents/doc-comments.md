# Doc Comments

Every method and exported function in this repo carries a JSDoc block, so a
contributor hovering a symbol in their editor learns what it does, what it
expects and what it gives back without opening the file. That is the one
exception to CLAUDE.md's "No comments" rule: a `/** */` block directly above a
function or method is allowed and expected; inline `//` comments, banners and
prose inside a body are still banned. Your job is to find every function that
lacks one, write it, and fix the ones that lie.

## Scope

In scope:

- `src/lib/**/*.ts` and the `<script>` of `src/lib/components/**/*.svelte`
  (exported functions and functions a component exposes via `export function`)
- `src/hooks.server.ts`, `src/hooks.client.ts` if present
- `scripts/**/*.ts`

Out of scope, skip entirely:

- `cmd/worker/**/*.go`, `cmd/cli/**/*.go`, `cmd/installer/**/*.go` (and their
  shared `internal/**/*.go` libraries) — separate Go packages, not TypeScript.
  Go has its own doc-comment convention (`// FuncName does X`, no `/** */`, no
  JSDoc tags), already followed there; this agent's JSDoc-specific rules below
  don't apply to them. `cmd/installer/` and the standalone `cmd/agent/` (later
  merged into `cmd/worker` as its agent mode) were both Bun/TypeScript
  sub-projects (in scope for this agent) before their Go rewrites; the agent was
  the last to move.
- Route files (`src/routes/**`: `+page*`, `+layout*`, `+server.ts`). Their
  `load`/`actions`/`GET` shape is framework-defined.
- `src/lib/components/ui/**` (shadcn-svelte primitives, regenerated by the CLI)
- Generated output: `openapi.json`, `homerun.schema.json`,
  `tests/integration/support/openapi-types.ts`, `drizzle/**` migrations,
  `.svelte-kit/**`, `build/**`
- `tests/**` and any `*.test.ts` / `*.spec.ts`
- `src/lib/server/db/schema.ts` table definitions (not functions)

What counts as needing a doc comment:

- Every class method: public, `#private`, `static`, `get`/`set` accessors,
  `constructor` only when it does more than assign fields.
- Every `export function` / `export async function`.
- Every `export const x = (...) => ...` / `export const x = async (...) => ...`.
- Mixin factories (`export function SomethingMixin(Base)`) and the methods of
  the class they return.
- Non-exported module-scope helpers are **not** required, unless they are longer
  than ~15 lines or their name doesn't make the behaviour obvious.

## Workflow

1. **Inventory.** Build the list of candidates with a script, not by eye. A
   quick Bun/TS script in the scratchpad using the TypeScript compiler API
   (`typescript` is already a devDependency) that walks the in-scope files,
   visits `MethodDeclaration`, `GetAccessor`, `SetAccessor`,
   `FunctionDeclaration` with an export modifier, and `VariableStatement` with
   an export modifier whose initializer is an arrow/function expression, and
   reports `file:line name` for each node where `ts.getJSDocCommentsAndTags`
   returns nothing. For `.svelte` files, extract the `<script>` block first. If
   the caller gave you a diff or file list, restrict to those files.
2. **Read before writing.** For each candidate, read the whole function and its
   call sites (`grep -rn "\.name(" src scripts`) until you actually understand
   what it does. A doc comment that paraphrases the name ("Gets the service") is
   worse than useless; don't write one.
3. **Write the block.** House style:

   ```ts
   /**
    * Pulls the image for a service and recreates its container, reusing the
    * existing network and volume attachments.
    *
    * @param service The service row to redeploy.
    * @param opts.force Recreate even when the image digest hasn't changed.
    * @returns The new container id.
    * @throws When the image can't be pulled from its registry.
    */
   ```

   - First line: one sentence in the present tense saying what it does and,
     where it isn't obvious, why a caller would use it over a neighbour.
   - Mention side effects that aren't visible from the signature: writes to the
     DB, Docker calls, network requests, enqueued jobs, cache mutation, thrown
     errors, anything stateful like `SystemStatsService`'s CPU sample.
   - `@param` only for parameters whose meaning isn't carried by name + type;
     never restate the TS type in braces (`{string}`), TypeScript already has
     it.
   - `@returns` only when the return value isn't obvious from the name/type.
   - `@throws` when the function throws on a path callers must handle.
   - Trivial one-liners (a getter returning a field, `toJSON()`) get a single
     line:
     `/** The service's public URL, derived from its slug and base domain. */`
   - Plain English, no markdown headings, no `@author`/`@since`/`@example`
     unless an example genuinely prevents misuse.

4. **Fix stale blocks.** While you're in a file, compare each existing JSDoc
   against its signature and body: `@param` names that don't exist, missing
   params that need one, a summary contradicting what the code now does. Fix
   them.
5. **Keep edits to comments only.** Don't rename, reformat or refactor code. If
   you spot a real bug, add a line to `TODO.md` and move on.

## Verify

- Re-run the inventory script: zero missing in scope (or in the files you were
  given).
- `bun run lint` and `bun run type-check` must still pass; a malformed block can
  break biome or svelte-check.

## Report

Say how many candidates you found, how many you documented, how many stale
blocks you fixed, per top-level area (`src/lib/services`, `src/lib/dto`,
`scripts`, ...). List anything you skipped because you couldn't work out what it
does from the code, with `file:line`, rather than guessing.
